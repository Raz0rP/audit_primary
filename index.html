Contrastes couleurs

Le ratio de contraste mesure la différence de luminosité entre un texte et son fond. En dessous de 4.5:1, le texte est difficile à lire pour des personnes malvoyantes, âgées ou dans de mauvaises conditions d'éclairage. Seuil WCAG AA : 4.5:1 pour le texte courant, 3:1 pour les grands titres et icônes.

Typographie — Bento

Analyse du fichier bento/lib/src/typography.dart. Seuils de référence : 11 sp est la limite basse d'Apple HIG pour du texte secondaire ; 14 sp est recommandé pour le texte courant. Le style de base utilise height: 1.3 — en dessous du 1.5× recommandé par WCAG pour les paragraphes.

bilans (sommeil, activité, addiction) · préconsultation · objectifs · dropdown

▼

Référentiels & règles

Toutes les règles citées dans cet audit, expliquées en langage courant. Chaque critère est lié à sa source officielle. Les niveaux A sont obligatoires, AA est la cible standard (WCAG), AAA est le niveau optimal.

WCAG — Perceptible (1.x)
1.1.1 A Contenu non textuel WCAG 2.1 ↗

Toute image qui apporte une information doit avoir un texte alternatif — une description courte lisible par les technologies d'assistance. Une image purement décorative doit au contraire être masquée pour ne pas polluer la lecture.

Dans Primary Les photos de médecins (avatars) n'ont aucun texte alternatif. Un utilisateur aveugle ne sait pas quel médecin est affiché — issues A1, B3.
1.3.1 A Information et relations WCAG 2.1 ↗

La structure visuelle d'une page (titres, listes, groupes de champs) doit être transmise par le code, pas seulement par l'apparence. Un titre qui ressemble à un titre doit l'être aussi techniquement — sinon une personne non-voyante ne peut pas s'en servir pour naviguer.

Dans Primary Les en-têtes de mois dans les listes (« AVRIL », « MAI ») sont stylisés comme des titres mais n'en sont pas — issues C3, B6.
1.4.3 AA Contraste du texte WCAG 2.1 ↗

Le texte doit avoir un ratio de contraste d'au moins 4.5:1 par rapport à son fond (ou 3:1 pour les grands textes). Ce ratio se calcule à partir de la luminosité relative des deux couleurs selon une formule standardisée.

Pourquoi ce chiffre ? Il correspond au niveau de contraste minimum pour qu'une personne ayant une acuité visuelle de 20/40 — fréquent chez les personnes âgées ou après 40 ans — puisse lire confortablement.

Dans Primary Le gris #8C8C8C (ratio 3.4:1), le rouge erreur #FF5A5A (3.1:1) et le vert succès #22AF5C (2.7:1) sont tous en dessous du seuil — issues B1, E2.
1.4.4 AA Redimensionnement du texte WCAG 2.1 ↗

Le texte doit pouvoir être agrandi jusqu'à 200 % sans perte de contenu ni de fonctionnalité. Sur mobile, cela se traduit par le respect du paramètre d'accessibilité « Grande police » du système (iOS Dynamic Type, Android Font Scale).

Environ 20 % des utilisateurs mobiles activent une taille de police supérieure à la normale. Ce n'est pas seulement une question de handicap — c'est aussi une question de confort pour tout le monde.

Dans Primary Certains composants Bento bloquent ou ignorent l'agrandissement, causant des débordements et des troncatures — issue B7.
1.4.10 AA Reflow WCAG 2.1 ↗

Le contenu doit pouvoir s'afficher sur une largeur équivalente à 320 px CSS sans nécessiter de scroll horizontal. Sur mobile, cela signifie que les layouts doivent s'adapter à la taille de texte sans déborder de l'écran.

Dans Primary Les cards en Row fixe (cartes RDV, équipe médicale) peuvent déborder en grand texte — issue B7.
1.4.11 AA Contraste des composants non-textuels WCAG 2.1 ↗

Les éléments d'interface (boutons, champs, icônes informatifs) doivent avoir un ratio de contraste d'au moins 3:1 par rapport à leur environnement. Ce seuil est moins strict que pour le texte car les éléments graphiques sont généralement plus grands.

Dans Primary Les indicateurs d'état en vert succès (#22AF5C, ratio 2.7:1) sont en dessous du seuil pour les composants — issue B1.
1.4.12 AA Espacement du texte WCAG 2.1 ↗

Quand un utilisateur modifie l'espacement du texte (interlignage, espacement entre lettres ou paragraphes), le contenu ne doit pas devenir illisible. Concrètement, l'interlignage des paragraphes doit supporter au moins 1.5× la taille de la police sans casser le layout.

Dans Primary Le style de base Bento utilise height: 1.3 — en dessous du 1.5× recommandé pour les textes courants — issue D4.
WCAG — Utilisable (2.x)
2.1.1 A Clavier / navigation séquentielle WCAG 2.1 ↗

Toutes les fonctionnalités doivent être accessibles sans pointeur (souris, tactile). Sur mobile, cela signifie que les lecteurs d'écran doivent pouvoir atteindre et activer tous les éléments interactifs en balayant l'écran.

Dans Primary Les zones de tap de la visionneuse document ne sont pas détectées par le lecteur d'écran — issue A2.
2.2.2 A Pause, arrêt, masquage WCAG 2.1 ↗

Tout contenu qui bouge ou clignote automatiquement doit pouvoir être mis en pause, arrêté ou masqué par l'utilisateur. Les animations qui durent plus de 5 secondes sont particulièrement concernées.

Dans Primary Les animations Lottie et shimmer jouent sans possibilité d'arrêt — issue C1.
2.3.3 AAA Animation depuis des interactions WCAG 2.1 ↗

Les animations déclenchées par une interaction utilisateur doivent pouvoir être désactivées, sauf si elles sont essentielles. iOS et Android exposent un paramètre système « Réduire le mouvement » à cet effet.

Même si ce critère est AAA (optimal), il est facilement implémentable en Flutter avec MediaQuery.disableAnimations et son impact est concret pour les personnes souffrant de sensibilité vestibulaire.

Dans Primary Aucun composant ne lit le paramètre « Réduire le mouvement » du système — issue C1.
2.4.6 AA En-têtes et étiquettes WCAG 2.1 ↗

Les titres et étiquettes doivent décrire le sujet ou le but du contenu qu'ils introduisent. Un titre « AVRIL » doit être reconnu comme titre de section, pas comme texte ordinaire.

Dans Primary En-têtes de mois, titres de panneaux, cartes de rendez-vous sans résumé structuré — issues A6, B2, B6, C3.
2.5.3 A Étiquette dans le nom WCAG 2.1 ↗

Pour un composant interactif avec du texte visible (ex. un bouton « Fermer »), le nom accessible utilisé par les technologies d'assistance doit contenir ce texte visible. Cela permet aux utilisateurs de commande vocale d'activer un bouton en disant son nom.

Dans Primary Les boutons icône (fermer, partager) n'ont ni texte visible ni tooltip — issue C6.
2.5.5 AAA Taille de la cible tactile WCAG 2.1 ↗

La zone cliquable d'un élément interactif doit mesurer au moins 44 × 44 pixels CSS. Ce critère est AAA dans WCAG 2.1 mais est passé AA dans WCAG 2.2 (sous 2.5.8) avec un seuil ajusté.

Apple HIG recommande 44 × 44 pt minimum. Material recommande 48 × 48 dp. Ces deux recommandations de plateau convergent vers la même valeur physique.

Dans Primary Bouton fermer du BottomSheet, icônes d'action dans document_details, barre de navigation — issue C8.
2.5.8 AA Taille minimale de cible (WCAG 2.2) WCAG 2.2 ↗

Nouveau dans WCAG 2.2 : la zone cliquable doit faire au moins 24 × 24 pixels CSS (seuil minimum AA), ou si elle est plus petite, il doit y avoir suffisamment d'espace autour pour éviter les erreurs de tap. C'est moins strict que 2.5.5 mais est obligatoire au niveau AA.

Dans Primary Même zones que C8 — certaines icônes sont probablement en dessous de 24 dp également.
WCAG — Compréhensible (3.x)
3.3.1 A Identification des erreurs WCAG 2.1 ↗

Quand une erreur de saisie est détectée automatiquement, l'élément en erreur doit être identifié et l'erreur décrite à l'utilisateur en texte. Un message d'erreur uniquement visuel (bordure rouge) n'est pas suffisant.

Dans Primary Formulaire de connexion et upload de document — les erreurs sont génériques et positionnées loin du champ concerné — issue C11.
3.3.2 A Étiquettes ou instructions WCAG 2.1 ↗

Les champs de formulaire doivent avoir une étiquette visible et liée programmatiquement au champ. Il ne suffit pas qu'un texte soit affiché à côté du champ — il faut qu'il soit associé par le code pour que le lecteur d'écran fasse le lien.

Dans Primary Le TextField Bento affiche le label comme Text séparé, sans lien avec le champ — issue B4. La case CGU a le même problème — issue A3.
3.3.3 AA Suggestion en cas d'erreur WCAG 2.1 ↗

Quand une erreur est détectée et qu'une correction est possible, des suggestions doivent être proposées. Dire « Code incorrect » n'est pas suffisant — « Ce code est incorrect, vérifiez le SMS reçu » l'est.

Dans Primary Messages d'erreur OTP et validation de formulaire — issue C11.
WCAG — Robuste (4.x)
4.1.2 A Nom, rôle, valeur WCAG 2.1 ↗

C'est le critère le plus cité dans cet audit. Tout composant interactif doit exposer trois informations aux technologies d'assistance :

  • Nom — ce que c'est ou ce que ça fait (ex. « Ouvrir la messagerie »)
  • Rôle — la nature du composant (bouton, case à cocher, liste…)
  • Valeur — l'état actuel quand pertinent (coché/non coché, sélectionné, désactivé…)
Dans Primary Violations dans A1, A2, A3, A4, A6, B2, B6, C5, C6, C7 — le critère le plus fréquemment enfreint.
4.1.3 AA Messages de statut WCAG 2.1 ↗

Les messages de statut qui apparaissent sans déplacer le focus (chargements, confirmations, erreurs) doivent être annoncés automatiquement par les technologies d'assistance. En Flutter, cela se fait avec liveRegion: true dans le widget Semantics.

Dans Primary Spinners de chargement (B5), barre de progression (A5), bouton en chargement (C7), barre d'étapes Bento (C2).
Recommandations plateformes
Apple HIG VoiceOver & accessibilité iOS Apple ↗

Apple définit plusieurs règles spécifiques pour iOS. Les principales pour une app Flutter :

  • Taille minimale des cibles — 44 × 44 pt. En dessous, les utilisateurs font des erreurs de tap, surtout avec des doigts plus larges ou des tremblements.
  • Dynamic Type — respecter les tailles de police définies par l'utilisateur dans les réglages. Une app qui bloque l'agrandissement viole cette recommandation.
  • Reduce Motion — lire UIAccessibility.isReduceMotionEnabled (ou son équivalent Flutter MediaQuery.disableAnimations) et ne pas jouer les animations si activé.
  • Taille de texte minimale — 11 pt pour du texte secondaire uniquement. Toute information principale devrait être à 13 pt minimum.
Material 3 TalkBack & accessibilité Android Material ↗

Les recommandations Material convergent avec Apple HIG sur la plupart des points :

  • Touch target minimum — 48 × 48 dp (légèrement plus grand qu'Apple). La zone tactile peut être plus grande que l'élément visuel grâce au padding.
  • TalkBack — chaque élément interactif doit avoir une description. Les éléments décoratifs doivent être marqués importantForAccessibility="no" (Flutter : ExcludeSemantics).
  • Font scale — Android permet d'aller jusqu'à 200 % sur certains appareils. Les layouts doivent s'adapter sans casser.
COGA Accessibilité cognitive W3C COGA ↗

Le groupe de travail COGA (Cognitive and Learning Disabilities Accessibility) du W3C a produit des recommandations complémentaires aux WCAG, spécifiquement pour les troubles cognitifs, d'apprentissage et de mémoire. Ce n'est pas un standard contraignant, mais un guide de bonnes pratiques très utile dans un contexte médical.

  • Simplicité — une seule action principale par écran, pas de surcharge d'information.
  • Langage clair — éviter les acronymes et termes cliniques non expliqués.
  • Erreurs bienveillantes — expliquer ce qui s'est passé et comment le corriger, sans jargon technique.
  • Cohérence — les mêmes actions produisent les mêmes résultats partout dans l'app.
Dans Primary Écrans denses sans hiérarchie claire, messages d'erreur génériques, acronymes médicaux dans les bilans — issues C9, C11.
